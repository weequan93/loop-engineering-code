# 项目监督与跨批次继续

`COMPLETE` 证明一个冻结批次的合同已通过，不能证明整个路线图完成。
例如 G1 数据基础增量完成后，身份、持久执行、存储、完整 G1 资格以及
G2–G5 仍可能未完成。之前的原生入口只返回批次结束，缺少后续批次衔接。

现在，宿主可把用户**已经授权**的后续工作登记为持久的有界队列。
这提供跨批次的状态和下一步；宿主仍负责实际思考、需求分析、专业分工与
执行。MCP 不会自行唤醒已结束的对话，也不保证模型持续遵循指令。

## 用户如何使用

用户一次说明整体目标、边界和实际外部决定，例如：

> 自动推进已授权的剩余项目需求直到验收完成。常规工程选择由主线程处理，
> 不要每批要求我再说继续。保留原验收、历史和累计用量；收费服务、发行、
> 新权限及需要真人参与的事项仍遵循原约定。先汇总剩余范围与有效额度，
> 提前提出真正缺失的决定，再登记有界的后续批次计划。

主线程负责操作工具。它先读取全项目规格、需求追溯、已接受的批次、实际
回答和授权，将剩余工作映射为明确的后续合同，并核对累计控制器额度。
登记多批队列前，应一次汇总整个队列的额度估算、最终检查和修复/集成储备，
并列出未知项。上一增量的剩余额度不是整个路线图的预算；仅批准下一批的
额度也不代表批准后面所有扩额。主线程应提前集中报告，而非每批重新发现。
原约定的停止边界仍有效；实际用户后来授权更广范围时应记录该授权，
不能每完成一个增量就重新要求常规续批确认。路线图本身不能代替授权。

## 宿主工具协议

1. `loop_project_supervise(team_id, objective, authorization, milestones,
   controller_budget_seconds)` 登记目标、真实授权文字、有顺序的 `{id, brief}`
   后续批次及已审定的累计额度。支持 1–16 个后续批次；队列与额度冻结后，
   原样重复是幂等的，直接放大范围或额度被拒绝。初次登记可在需求、规划、
   执行或有效的 COMPLETE 批次进行；已有执行合同的上限必须保留。
2. 完成当前批次后读 `loop_next`。`advance_project` 返回
   `loop_project_advance` 的参数；宿主在同一轮继续调用，无需用户另说继续。
3. `loop_project_advance` 只接受最新、候选有效、无缺失证据的已验收前驱。
   它先核对旧副作用与原费用策略，然后创建**空的 SPEC 阶段**，保留前驱
   COMPLETE。用返回的**新 team_id** 调用 `loop_next`，提交新需求和计划，
   经过原预检、范围、检查、独立评审及交接门槛再执行。不会重放旧工作流。
4. 创建与队列绑定在同一受认证的首条批次事件中。回复丢失、重连或重复调用
   返回已建立的后续批次；项目锁和团队创建门槛拒绝并发重复创建。
   对历史前驱调用 `loop_next` 会返回 `follow_project_batch` 指向最新批次。
5. `loop_project_control` 接收真实用户的 `pause`、`resume`、`cancel`。
   暂停同时停止最新未完成批次；重连不解除暂停。取消队列是终止操作。
   已完成的前驱状态、原检查和用量不改变。
6. `loop_project_budget_amend(team_id, amendment_id,
   expected_controller_budget_seconds, controller_budget_seconds,
   authorization, reason)` 在**实际批准具体新额度后**，追加原队列的正式扩额
   记录。根或后续批次 ID 指向同一账本。预期旧上限必须等于当前有效上限，
   新上限是绝对秒数，必须增大且不超过 2,592,000 秒。最多保留 64 次修订。
   相同 ID 与相同内容重试不会重复增加；相同 ID 的不同内容、过期预期、
   减额、暂停/取消后的新修订均拒绝。丢失回复可按原参数恢复。

扩额只改变项目链累计控制器上限。原登记声明、已用毫秒、合同、任务时限、
检查、独立评审尝试和收费策略不改；不会恢复暂停，也不会派发模型或开发。
额度修订以受认证的团队事件记录，并在进度和规划上下文中呈现真实批准。
原生宿主填入的批准文字仍是宿主声明，框架不能独立鉴定其来自真人。

例如某队列原上限为 10,197 秒，已用 897 秒，下一批保守预留 19,440 秒，
规划预检会给出缺口 10,140 秒、最低累计上限 20,337 秒。实际批准后可调用：

```json
{
  "team_id": "原项目的根或当前后续批次 ID",
  "amendment_id": "g1-f02-controller-cap-20337",
  "expected_controller_budget_seconds": 10197,
  "controller_budget_seconds": 20337,
  "authorization": "填入用户实际批准本次新上限的原文",
  "reason": "已审阅的 G1-F02 合同预留 19440 秒，保留全部原检查和评审储备"
}
```

该示例不替实际项目获得批准；20,337 秒只满足这份下一批提案，不代表覆盖
后面所有里程碑。使用返回的最新 `team_id` 继续预检和原规划提交；原队列
原样重登记仍幂等，不能通过重登记新上限替代正式修订。

需求与规划包保留项目目标、实际授权和剩余额度。真实服务、设备、权限、
发行和消费决定在需求收集时提出；队列不替用户回答问题。仍可在当前批次
中继续不依赖缺失外部条件的授权工作。

## 用量与验收边界

- 累计额度覆盖**登记的根批次及其后续批次链**。更早的项目批次保留各自
  原账本；不要将本链的数字冒称整个开发历史的总用量。
- 同一子运行或集成运行只计一次，保留精确毫秒，预算秒数向上取整。
  丢失已记录子运行不能被计为零。新的规划预检会显示剩余额度，并保守
  预留每项任务的子运行及可能的集成运行完整时限。提交不能超过当前有效
  累计额度；扩额后仍检查该门槛，缺失原子运行账本继续拒绝。
- 新批次中的任务、检查、评审尝试、观察和返工仍保留各自冻结限制。
  未完成或超额批次不能靠续批重置，后续批次也不能重新登记一条新队列。
- 宿主对话、原生专业 agent 的 token 与费用仍未知；本机制没有硬消费
  保证或独立 OS 隔离声明，硬费用策略继续拒绝不具备计量能力的原生路线。
- `project_queue_complete` 只表示登记队列中的合同全部接受。全产品完成还
  要核对完整需求追溯；未列入范围和真实外部资格不能被暗示为通过。
  真实缺口需要具体的审定扩展，不能静默新建队列来增加预算。

进度页显示项目目标、最新批次、已建立的后续批次数、续批链累计额度与
下一步，并明确区别批次验收和完整产品验收。

## 更新与验证

先重连框架后端，读取 `project_batch_succession` 功能标记；使用扩额入口时
还需确认 `project_budget_amendments` 与 `loop_project_budget_amend` 已加载。
核对完成候选仍
有效，再按已有实际授权登记队列。该步骤可通过后端工具完成，毋须先改动
旧项目内的技能文件。旧项目未登记队列时仍按原批次停止，不能猜测更广授权。

新设置使用最新模板；原 `host-install` 入口可升级精确的已发布技能，并保持
自定义技能和冻结合同。更新项目内的技能可能改变候选；已变化的旧候选不能
被冒称仍然有效，应按具体变化建立审定的新基线，保留旧验收与历史。
框架升级本身不替真实项目登记队列、派发开发或修改验收历史。

离线案例覆盖实际本地子运行与交接、两次验收后续批、重复调用、创建回复
丢失、重连、并发创建、暂停取消、真实问题、累计预算预检及提交拒绝、
旧证据和费用门槛、错误项目、框架变化与页面转义。默认测试不派发模型。
扩额离线案例验证同一账本、原证据与用量保留、早期缺口与提交门槛、重连、
丢失回复、失败提交、并发预期冲突、暂停取消、无效授权参数和缺失用量拒绝。
实际宿主在长任务中持续执行仍属于单独的实时评估，必须先通过当前完整
离线验证和实现就绪检查。
