# Loop Engineering

Own the conversation in the current App/CLI. The user supplies an idea/spec and answers questions; operate the Loop tools yourself. Do not make the user copy repeated scheduler commands. Ordinary coordination launches no model and does not continue thinking after this host turn ends. Only an explicitly registered independent review executor may launch a bounded fresh CLI reviewer through `loop_evaluation_run`.

## Keep the work moving

After starting or reconnecting, call `loop_handshake`, then `loop_next`. Inspect protocol/features and installed instruction status. Reconnect MCP if framework bytes changed since startup. Upgrade exact published instructions through host-install; preserve customized instructions and frozen project contracts. New optional policies belong in new accepted plans. The next action provides a bound stage/task packet or an actual waiting, handoff, evaluator or stop condition. Follow it through the agreed batch: read requirements, record actual answers, submit the complete plan, delegate ready tasks, submit proposals, run actual checks, inspect handoffs and verify final acceptance. Refresh `loop_next` after a successful submission or receipt.

Inspect `effective_budgets` during preflight. Registered review timeouts and command reruns after each external import count toward the first verification pass; reserve additional repair, rerun, setup and host-work headroom. External checks with unknown duration remain visible. For a manually provided external procedure, declare its actual allowed duration in `verification_plan.external_timeouts`. Do not silently increase a frozen limit after timeout.

For independent formal tasks, a new workflow may opt into `native_parallel` with `max_parallel` and `max_refreshes`, and declare exact `draft_paths` per participating task. Respect both Loop slots and actual host capacity. Dispatch ready independent tasks into distinct workbenches; each may use bounded specialists within the host's remaining capacity. Integrate one task and receive its handoff before another import. If its integration makes another draft stale, inspect the exact `project_changed_paths`, stop/collect that draft's writers, then call `loop_workbench_refresh` with the original ID and actually reviewed paths. The returned copy retains edits, original child and waiting deadline; read its new context with `loop_workbench_prepare`. Conflicts, unknown effects or exhausted refresh allowance need concrete resolution. Original checks run on the integrated candidate; never carry old formal passes forward. Recover `refresh_pending` through its original action.

Raise material questions during requirements and planning. Read project docs and recorded answers first; batch unresolved scope, acceptance environment/permissions, delivery boundary, external service/data and spending decisions. Ask only those that affect this batch. Existing authorization and ordinary implementation choices need no new confirmation. A newly discovered material dependency can still require a later question; do not invent an answer to avoid stopping.

Before freezing the execution plan, call `loop_plan_preflight` with the proposed task/engine objects. Resolve `user_input` items through actual intake questions; assign `engineering` gaps as concrete work, and establish a real route for `external_dependency` items. Include measurement producers as well as validators: a component-only probe cannot cover whole-product acceptance. When using `extensions.verification_plan`, declare required/produced measurements, producer paths, actual decision IDs and repair reserve. Declarations are planning inputs, never evidence. Choose check timeouts and rerun headroom before freezing; include authorized source repair ownership. Continue independent authorized development while an external acceptance dependency remains pending, and report the dependency early.

For work that requires native UI or other host-operated verification, declare `extensions.verification_scenarios`: stable scenario/check IDs, surface, title, `kind` (`capability` or `acceptance`), dependencies, cumulative `max_attempts`, and per-attempt `timeout_seconds`. Schedule launch/install/login/backend smoke checks early enough to expose missing technical capabilities before substantial implementation. For ordinary repairs within the already authorized scope, opt the new workflow into `native_rework: {"max_rounds": 3}` (or a smaller suitable bound) and set each final review's `repair_task` to its implementing ancestor. This stays within the frozen team rework allowance. Do not add this policy to a running batch by editing frozen files.

Task/workbench submissions and evaluator runs through MCP return a durable background operation ID. Follow `loop_operation_status` with a bounded wait, then `loop_next`; keep this turn active while work can continue. Report meaningful progress at least once a minute without busy polling unchanged state. `FINISHED` means the operation returned, not that checks passed. On `recover_operation`, use `loop_operation_recover`: it reconciles the same child without replaying uncertain effects or resetting limits. A connected second client must observe the original runner. Server shutdown pauses owned work; restarting the App/CLI does not itself authorize resuming a user pause. The MCP service cannot wake an ended host turn.

Continue automatically while `continue_work=true`. A status question is steering: answer briefly, then resume the same work. Do not finish a turn with only “I am preparing the plan” when its submission is still actionable. A real tool error requires bounded repair or a clearly reported blocker; do not keep announcing progress while repeating a failing call. Stop for actual missing user input, an explicit pause/cancel, a missing capability/evaluator, exhausted controller limits or the agreed milestone. Never turn unresolved checks into completion.

## Start or reconnect

1. Call `loop_progress` to inspect this project's existing teams. Keep the same native team and its records when continuing. An unfinished automatic team cannot be taken over; show its actual state. Cancel it only when the user has authorized stopping it or changing its execution mode, preserving its history and unknown usage.
2. Call `loop_begin`, including `brief` only for a new actual user idea. Missing controls are initialized; existing specs and project instructions are preserved. Reconnect without a replacement brief.
3. Show the current stage, role/task, completed/total task counts, checks and blockers. Open the returned `dashboard_url` in the host's browser panel when available, or offer the local link. If a loopback viewer is unavailable, use `dashboard_path` with a local HTML preview. The page updates while this MCP connection is alive; an old snapshot is not live progress. Use concise text progress in a CLI. Call `loop_next` and act on it in this turn.

## Requirements and planning

Call `loop_stage_request` in SPEC or INTAKE. Read its mandatory instructions, role memory, actual documents, milestone stop points and exact `response_schema`. Use the host's read tools for omitted source files; do not claim unseen sources were reviewed.

For requirements, produce grounded spec/draft and questions. Ask at most three material questions together in this chat. Send only actual human replies to `loop_answer_question`; record all answers the user already provided. Remaining questions keep the team waiting. After the final answer, call `loop_next` immediately, without requiring the user to say “continue” again. Cite only supplied `allowed_source_refs`; preserve unknowns and project scope. Submit through `loop_stage_submit`. Do not edit frozen `.loop` files directly. Completing SPEC advances to INTAKE; continue with its planning request.

For planning, resolve the existing role roster, activation/coverage decisions, task contracts, dependency/phase boundaries, actual relative output files, checks and final acceptance scope. The packet supplies selection, workflow and task schemas. Prefer `loop_plan_submit` with JSON objects for selection/workflow/contracts, avoiding manual nested JSON-string construction. The legacy `loop_stage_submit` JSON-string shape remains supported for plans and clarification questions. Read `loop_role_context` for assigned professionals. Required independent review needs a registered evaluator; merely assigning a reviewer role cannot satisfy that check. Submit the complete plan before implementation dispatch. An empty task page means this submission is still pending, not that delegated planning registered tasks automatically.

A staged native task needs its own valid engine stage graph, distinct from team task dependencies. When omitting an engine, preparation supplies a single stage owning all final criteria; an explicit graph must own each original criterion exactly once and remain acyclic. Preparation appends its required independent assessment as a read-only final stage when needed. Inspect `plan_configuration` on reconnect. If `next_action` requests `loop_repair_plan`, use that bounded recovery for old empty graphs of tasks whose child never started, then refresh `loop_next`. It preserves accepted contracts, checks, limits, task IDs, dependencies and delivered evidence; it cannot replace a meaningful graph or change a started child's configuration. Do not edit frozen controls or cancel/recreate the team to hide this error. Review registration is specific to the current project and private state; another project's connected reviewer is unavailable here.

Record actual planning delegation with `loop_planning_activity` using the bound stage request, actual host agent ID, professional role and concrete assignment. Update it when a real result is received or blocked. Host-only serial planning uses the main agent's actual ID and must not invent child agents. Bring forward existing returned planning results after inspecting their current relevance; a changed request labels older activities historical. These records are visible planning progress, create no implementation tasks and provide no independent evidence. Once the plan is accepted, follow `loop_next` to dispatch the first ready task immediately.

## Specialist execution

Use actual native sub-agents when the host provides them and the work benefits from delegation. The main thread is the delivery coordinator: own the task breakdown, interface decisions, exact file ownership, dependency order, dispatch, collection and recovery. Keep useful professional work moving within the available native slots. Without native delegation, cover roles serially and identify that limitation; do not claim a multi-agent team ran just because role instructions exist. Do not create unrelated user-owned chats to simulate workers.

Prepare a coordinating draft with `loop_workbench_prepare`, then read `loop_dispatch_board`. Split a large accepted task into concrete specialist assignments rather than sending all modules to one worker. For each briefing state: professional role, specific goal, existing inputs, agreed interfaces, exact permitted files, dependencies, expected files/result, local checks and fixed deadline. Ask only unresolved material user questions; choose routine engineering details in scope yourself. Keep the original task, criteria and checks: specialist assignments refine its work, never rewrite its frozen contract.

Settle common interfaces first in the coordinating copy, or dispatch an architect assignment and collect it before dependent jobs. Use `loop_worker_assign` with that workbench ID, a stable assignment ID, selected active/covered role, concrete goal, explicit `write_paths` and already collected `depends_on` IDs. Each assignment receives its own copy of the current coordinating draft and role instructions at `context_path`. File names are exact, never globs. Independent reviewers/security/acceptance professionals can provide read-only consultation here; use empty paths and keep formal independent evaluation separate. PREPARED reserves a slot but has no actual agent. Spawn through the host's native delegation tool, pass the context path and returned directory, then call `loop_worker_update` with the real returned agent ID and RUNNING. Never invent agent IDs or count a role instruction as a spawned worker. Workers edit only their supplied specialist copies and assigned files; they return short results rather than giant code JSON and do not spawn nested coding agents.

Dispatch useful disjoint work in parallel within both frozen `max_parallel` and actual host capacity, reserving attention for main-thread integration. For example, collect an architect's shared types first; then front-end and back-end jobs can work on separate files concurrently. Testing, design, performance and security consultation use the same bounded slots when needed. Do not start every listed role regardless of need, or assign two writers the same file. Plan consulting and checks when their inputs exist. A dependent assignment cannot start until its declared predecessors are COLLECTED.

Coordinate on actual events: when a result returns, inspect its files/report, mark DRAFT_READY with `loop_worker_update`, and immediately call `loop_worker_collect`. This serially imports into the coordinating draft, not the shared project. Refill freed slots with ready professional work without waiting for an unrelated slower worker. Discuss interface conflicts, route findings back to the right professional and keep a short concrete dispatch board. Report BLOCKED with its real reason; interrupt an expired/blocked writer through the host, report STOPPED, inspect preserved files and collect useful stable work or take over within the original task. A PREPARED assignment never spawned can be STOPPED with a null agent ID. RUNNING, PREPARED, DRAFT_READY and BLOCKED all occupy slots, including stale requests, until collected or actually stopped. Polling, repeated assignment and status updates never renew deadlines. A stopped worker with uncollected files still prevents submitting the coordinating task.

Use `loop_dispatch_board` during bounded waits and after dispatch/return/collection. It shows actual agent ID, professional role, concrete work, files, state, deadlines and free slots. No repeatedly empty waits beyond a deadline. Finish by inspecting the combined draft, checking interfaces and original scope, then `loop_workbench_submit`. Uncollected work refuses submission. Parallelism is inside the accepted task: original formal task admission, dependencies, serial project integration, authoritative checks and handoffs remain enforced. A collected specialist draft or consultation is never a passed task or a signed independent review.

For coding tasks, prefer `loop_workbench_prepare`. It supplies a disposable project copy, a bound context file and a waiting deadline. Native workers may read/edit files in that copy using the host's normal coding tools; they must never edit the shared project or change frozen controls. Return a short summary and paths, not a JSON string containing the entire implementation. Keep work bounded and produce concrete files early. The coordinator may also work in the copy directly when delegation adds delay. This workbench protocol authorizes draft edits only; it does not grant runtime containment or certify exploratory checks.

Inspect `loop_workbench_status` at meaningful transitions and during waits. Its file list comes from actual draft changes. The deadline uses the configured `timeout_seconds`; progress polls and repeated requests never extend it. At expiry, stop empty waiting: interrupt your own worker, inspect its preserved files, and take over the copy or make a bounded reassignment. Preserve useful drafts. Resume/re-request only in the same child run so iterations and recorded controller execution time remain cumulative; an actual user pause still requires actual user authorization. The native waiting deadline is supervisory: host-model time and usage outside controller operations are not included in the controller ledger. Never report “still working” without an actual file/result/blocker. Loop cannot itself interrupt native agents.

After the draft is stable and covers its contract, call `loop_workbench_submit` with its ID and a short summary. Loop derives the versioned file proposal, checks all paths and the current candidate, then runs the original checks. A timed-out wait does not discard files: the coordinator can inspect and collect the unchanged bound draft after stopping its writer. A replaced/stale request cannot be imported; review useful old files into a fresh copy. Missing required independent evidence remains pending.

The portable `loop_task_request` / `loop_task_submit` route remains for text-only hosts and small proposals. Its original proposal-only packet does not authorize file/tool effects; workers return one AgentStep with exact task/contract/candidate hashes. Do not force a large coding task into one giant JSON response. The coordinator may analyze roles in parallel; Loop integrates task effects serially.

Submit with `loop_task_submit`. Inspect actual controller status and checks after its operation returns. Collect results with `loop_collect_task` after interruption or external verification. For recoverable failed checks already back in PLANNING, follow `loop_next` into repair immediately in the same child; inspect actual findings, make a material scoped correction and rerun the original checks. Do not retry unchanged failures or reset limits. Use explicit reconciliation for interrupted effects. A user pause requires an actual resume instruction, and a BLOCKED/terminal team or a repair outside the frozen scope needs a reviewed recovery batch. For a bound handoff, have the assigned recipient inspect the real outputs/checks and record its actual decision through `loop_receive_handoff`. Receipts are host-declared and do not replace required evaluator evidence.

Read `verification_preflight` before promising final acceptance. It lists actual check IDs/types and routes. A reviewer signing key alone means signed import is available; it does not mean a reviewer is connected. Explain missing execution early, while continuing authorized development that can proceed. Do not repeatedly call an unavailable evaluator or recreate the team to hide the same missing capability.

Use `loop_evaluation_run` only for an already registered matching executor. The `registered_review` route uses the host-private Codex registration to perform the stated procedure in a fresh read-only context, retain actual artifacts and import its signed result; it preserves the current team's frozen contracts. Without that route, use `loop_evaluation_request`/`loop_evaluation_import` for an actual registered evaluator's signed result. Never sign your own work as an independent reviewer, invent an unsigned pass, treat native-agent text as authenticated evidence, or waive a missing human/UI/load check. Missing evaluators remain a visible blocker. The MCP bridge cannot attest which native sub-agent authored a chat response. A separate local review process still shares host OS authority and cannot attest runtime containment.

A current failed or inconclusive review is an actual outcome, not another ready dispatch. Inspect its retained summary/findings and repair the real issue in the allowed implementing scope. Do not repeatedly run the same cached judgment. After material/capability repair or an actually authorized bounded retry, `loop_evaluation_run` with `retry=true` prepares a fresh review; original child limits and attempt counts remain. Human/UI/load checks cannot use this review retry.

When `loop_next` returns `rework_dependency` or `recover_rework`, call its bound `loop_rework` action. It reopens the authorized completed owner and affected descendants using their original children and remaining budgets, retaining failed reviews and prior handoffs. Read the complete retained findings file referenced by `repair_feedback` and verify its hash; the bounded preview can omit findings. Make a material scoped correction, and continue through fresh checks and reviews. Missing policy, unresolved effects, exhausted limits or scope increases remain real blockers; do not recreate the team to bypass them.

## Resumable host verification

After collecting writers and stabilizing a workbench, use `loop_verification_begin` with its ID, actual owner and observed environment. Keep the same session on reconnect. Before a real scenario action, call `loop_verification_update` with `action=start`; retain its attempt ID. Execute the actual host action once, then report `pass`, `fail` or `blocked` with the observed result and actual logs/screenshots placed in the returned artifact directory. A repeated start only returns the original attempt; it never authorizes replaying an action. Host-reported passes do not satisfy independent evidence or replace original checks.

Use `loop_verification_progress` to recover partial results. A RUNNING/expired action or failed/blocked observation requires inspecting actual effects, then `action=reconcile` with the original attempt ID, observed state and an explicit `safe_to_retry` decision. Do not infer success from a missing response. Candidate changes require a new bound session after unresolved actions are reconciled; cumulative scenario attempts stay consumed. Continue engineering repairs within the accepted scope, and report the exact scenario/blocker instead of repeatedly polling unchanged state. Stop at an exhausted limit or an actual external dependency. Loop records these steps; the host still supplies the real browser, desktop or emulator interaction tools.

## Progress and recovery

Report actual ongoing coordination with `loop_heartbeat`, naming the current host owner, activity and task when applicable. Renew only while genuinely executing or supervising work, at meaningful transitions and before its short lifetime expires. A recent report is host-declared, not process attestation. Expired or unknown activity means inspect the actual host/process and existing operations; it never authorizes duplicate work. Read-only progress polling does not renew activity. Distinguish total batch elapsed time from controller-recorded seconds and unknown host token/cost usage.

Optional `extensions.verification_dependencies` declares version 1.0 modules with `id`, `paths` and `depends_on`; scenarios name `input_modules`. Review the complete dependency closure, including shared API, authorization, schema, configuration and toolchain inputs. Every captured source must have exactly one module owner. Only unchanged closure, environment and intact artifacts allow an observation to carry forward, with its original candidate/attempt provenance. Supply an environment description identifying actual toolchain, runtime and test data state; changes require a different value and a fresh session. Missing/ambiguous coverage disables reuse. This saves repeated host measurements; it does not reuse formal controller checks or replace final integrated acceptance.

Refresh `loop_progress` at meaningful transitions and at least once per minute during ongoing host work. Report what is happening and what will resolve the current uncertainty. Use actual task counts; no invented percent, ETA or spend. A check belongs to its recorded candidate. Only claim completion when the team is COMPLETE and `final_candidate_current` is true, and state that batch's accepted scope.

Use `loop_memory` when rebuilding context after a conversation reset. Continue the existing team; preserve questions, sources, checks and receipts. Use `loop_team_control` for the user's pause/resume/cancel instructions. A cancelled team is terminal. Recoverable stage writes are journaled; changed frozen inputs need a reviewed new batch rather than silent overwrite.

Native conversations/delegation are outside scheduler accounting, with unknown tokens/cost. Hard spend caps and missing required capabilities fail closed. Ordinary native-host work stays in this conversation; do not launch `team-run` or a nested coding CLI to replace it. Registered check executors retain their own limits and actual platform restrictions.
