# Continuous development teams

The development preset supplies sixteen specialist roles. `team-run` connects
it to a continuous supervised scheduler: a coordinator prepares checked tasks
from the spec, workers propose changes in isolated working copies, controllers
run real checks, separate reviewer requests assess candidates, and recipients
inspect handoffs. Rejection schedules bounded repair and fresh acceptance.
The user provides requirements and answers material questions.

Each setup, coordinator, worker, reviewer and recipient request receives
[bounded role memory](team-memory.zh-CN.md), projected from signed team/child
records and frozen questions. Current tasks, actual answers, repair findings and
candidate-bound evidence indexes have explicit sources. Invalidated attempts
remain historical even if their bytes match a later candidate. Independent
assessments exclude implementer self-assessments. `team-memory TEAM_ID
--state-dir PRIVATE_STATE [--role ROLE --task TASK_ID]` inspects this context
without inference or budget changes. Resume the same team to retain its history.

Initialization, status, `team-start` and request export launch no model.
`team-run` explicitly dispatches work. Automatic scheduling does not establish
OS containment; the local backend remains operator-supervised.

## Start from a spec

If you only have an idea or docs, use the [setup requirements agent](requirements-setup.zh-CN.md)
first. `setup PROJECT --state-dir PRIVATE_STATE --adapter codex` makes a separate
requirements request, records real answers and writes the prepared spec. It stops
at `stage: INTAKE`; `team-run --team-id` continues that same accounted team.
An empty spec supplied to `team-run` takes this same setup stage before any
coordinator or implementation request. Nonempty-spec execution remains unchanged.

From the framework checkout with its Python environment:

```bash
.venv/bin/python scripts/loop.py init /absolute/project \
  --scenario development --spec /absolute/spec.md
.venv/bin/python scripts/loop.py team-run /absolute/project \
  --state-dir /absolute/private-state --adapter codex
```

The project must exist; private state must be outside it. `--adapter codex`
requires an installed authenticated Codex CLI. Each operation uses a fresh
noninteractive structured-output request in a read-only working copy. The
controller applies proposals. Optional `--model` selects a supported CLI model;
otherwise the installed CLI selects its default.

The coordinator prepares `.loop/team.json`, `.loop/workflow-tasks.json` and
contracts under `.loop/tasks/`. All control files are validated together in a
staged copy before journaled project writes. An existing nonempty workflow is
validated and executed directly. Status reports intake/execution, ready tasks,
original/integration run IDs, checks, cumulative budget and unresolved operations.
Invalid preparation returns validation findings to the coordinator for bounded
correction before any control files are installed. These revisions share the
same repair/dispatch budget; unavailable required procedures remain pending.
The framework supplies omitted native runtime/evaluator configuration and adds
the mandatory separate code assessment for independent roles before contracts
freeze. Existing criteria, command checks and human/UI/load/artifact requirements
are preserved. Review engines inherit the selected provider configuration or the
local template for a command/CLI host; actual inference still uses the selected
team host. Private evaluator registrations are generated by the controller.

Other hosts use `--adapter command --argv '["/absolute/host-wrapper"]'`: read one
JSON request on stdin and return one JSON result on stdout. `--adapter provider
--engine /absolute/provider-engine.json` uses the implemented OpenAI Responses
or Anthropic Messages transport, with credentials in operator environment
variables. Operation records retain the actual selected adapter/model; task
engine configurations separately specify check runtimes/evaluator registrations.
Claude Desktop uses the [native stdio MCP handoff](desktop-mcp.md) with
`--adapter desktop --review-adapter codex`. Desktop supplies queued proposals;
Codex performs separate fresh independent assessments. The file workflow remains
available. Desktop chat is supervised and its token/cost usage remains unknown.

## Answer and continue

Unanswered blocking questions stop at `AWAITING_INPUT` and remain recorded in
`.loop/questions.json`. Supply an actual answer and continue the same team:

```bash
.venv/bin/python scripts/loop.py team-answer TEAM_ID \
  --question QUESTION_ID --answer "Required behavior ..." \
  --state-dir /absolute/private-state
.venv/bin/python scripts/loop.py team-run --team-id TEAM_ID \
  --state-dir /absolute/private-state --adapter codex
```

The coordinator incorporates answers before freezing execution contracts.
After inspecting another recoverable waiting condition, use `team-resume`, then
`team-run --team-id`. Resume dispatches no process and resets no budget. Changed
specs, scope, checks or frozen instructions require a reviewed new team after
stopping/reconciling the old one. Required human, UI, load/security or artifact
procedures wait for an actual registered evaluator/executor; agent prose cannot
fabricate their execution or invent user answers. Frozen browser/HTTP plans
matching the exact check ID/type execute on branch and integrated candidates,
retain signed actual artifacts and reuse cached results after an import crash.

## Tasks and repair

Workflow schema `1.0` declares scope, tasks and a final task transitively
dependent on every other task. A task has this shape:

```json
{
  "id": "implement-api",
  "phase": "implement",
  "role": "backend",
  "task_file": ".loop/tasks/implement-api.json",
  "engine_file": null,
  "depends_on": [],
  "outputs": ["src/api.py", "docs/api.md"],
  "handoff_to": ["coordinator"],
  "repair_task": null
}
```

Contracts need meaningful criteria and actual checks. IDs, roles, phases and
recipients must match the selected team. Phase ancestors add dependencies to
`depends_on`; cycles, inactive roles, scaffolds and excluded outputs are refused.
Outputs must be nonempty regular verified files outside `.loop` and `.git`.
Declare actual relative file names, not descriptions. Admission rejects missing
outputs unless this task or one of its dependencies can create them within its
declared write scope. Existing regular files may be handed off by a read-only task.

Assessment tasks set `repair_task` to the implementing dependency that should
fix findings. It must be the task itself or an ancestor. Rejection creates fresh
attempts for that target and all descendants, invalidates old receipts and
supplies findings. Old attempts remain archived and charged. Accepted scope and
checks stay frozen. Failed checks within a child feed its next proposal;
terminal child budget exhaustion stops work. Integrated failures also route
back to repair. The coordinator remains responsible for faithful spec coverage;
completion covers the accepted contracts and final current candidate.

A fully received AgentStep that violates the proposal contract is rejected
before effects. Its validation finding enters the shared repair budget and the
next request uses a fresh ID/context. The same child keeps its iteration/time
and accounted usage; the rejected response remains recorded. Live input changes,
ambiguous dispatches and unavailable capabilities still require reconciliation.
Missing or empty declared handoff files also schedule bounded repair and fresh
downstream checks; passing command checks alone cannot complete that handoff.

## Parallel work, evidence and handoffs

Ready tasks run concurrently up to `max_parallel`, in private snapshot copies
with applicable task/scenario/repository instructions. These are working copies,
not Git worktrees: Git metadata and submodules are not provisioned. Declared
dependency installation and verified copies use frozen execution-tool plans;
other check dependencies must exist in the runtime. Use one worker when checks
share external state. See [execution tools](execution-tools.zh-CN.md).

AgentStep v0.2 proposals go through scope/hash validation and real controller
checks. Successful results integrate serially using preconditions and a durable
merge journal. A concurrent same-path edit stops integration and preserves the
current project. Automatic integration supports regular UTF-8 new/replaced files and, for
explicit AgentStep 0.3 contracts, deletion and bounded binary writes. It refuses
symlink and mode changes. The controller re-runs
checks on the actual integrated candidate before collecting a handoff.

Independent roles require native independent review checks. Separate fresh
review requests assess both the worker and integrated candidate. The trusted
wrapper signs the actual returned assessment with a registered private authority;
workers never receive its keys. This attests the wrapper's performed request and
retained response, not an independently authenticated human/provider identity.
Review requests retain the team's initial manifest and original excerpts of
changed files, plus verified predecessor check records/log excerpts for this
exact candidate. Predecessor evidence remains supporting material and does not
replace this task's required independent assessment.

Tasks progress through `PENDING`, `RUNNING`, `HANDOFF` and `COMPLETE`. Handoffs
contain candidate/output hashes and authenticated check artifacts. Every named
recipient inspects and accepts the current handoff before dependents unlock.
Receipts do not replace independent evaluator evidence. After all tasks pass,
final evidence must match the main candidate; `final_candidate_current` becomes
false if later edits change it.

Recipients receive the current task contract, candidate/environment-bound check
records, verified output excerpts, and changes within verified snapshots. Their
receipt assesses that phase; pending downstream review/acceptance remains gated
separately and cannot be mistaken for a missing check of the completed phase.

## Cumulative policy

Initialization supplies `.loop/team-policy.json`; `--policy` can select another
validated policy before starting. Its saved values remain frozen. Defaults:
two workers, forty admitted operations, three repair rounds, a one-hour absolute
team deadline and a three-minute operation timeout, with spend caps unset.

Coordinator, worker, reviewer and recipient calls share one ledger, including
failures and repairs. Native per-child admission limits remain enforced too.
`--max-cycles` bounds one scheduler invocation without resetting team limits.
The absolute deadline includes waiting for answers, pauses, crashes and recovery;
expiry cancels owned model/check processes. Distributed clocks/hosts are outside
this implementation.

Hard token/cost caps require verified provider input/output bounds and, for cost,
configured pricing in the budget currency. Responses are reserved before
dispatch. Optional final reserves protect headroom for the final task. Missing
or ambiguous usage retains conservative reservations as unknown. An exceeded
quote blocks proposal effects and later dispatch.

Generic command/Codex bridges cannot reserve a verified spend ceiling, so hard
spend caps refuse before process creation. With caps unset, time/dispatch/repair
limits apply. Complete Codex token events contribute reported total tokens;
the bridge does not establish prices or input/output allocation. Unreported
command usage and Codex cost remain unknown. The ledger covers this scheduler's
operations, not arbitrary outside calls or other team IDs. Automatic teams
refuse manual worker routes that bypass accounting. Operator-owned state is not
a sandbox against a privileged operator.

## Stop and recover

Use `team-pause`, `team-cancel`, `team-resume`, `team-audit` and `team-runs` with
team ID and `--state-dir`. Pause/cancel stop owned processes; cancel is terminal.
One scheduler lock owns a team. Short metadata locks let isolated workers overlap.
Reserved child IDs, copy bases, merge identities and control-write journals
survive crashes. Complete responses and saved reviewer packets can be reused
before consumption. Resume preserves accumulated usage and held reservations.

An admitted operation without a complete response blocks new dispatch until
inspection and reconciliation:

```bash
.venv/bin/python scripts/loop.py team-reconcile TEAM_ID \
  --operation-id OPERATION_ID --note "Inspected ...; the owned process is stopped." \
  --state-dir /absolute/private-state
```

Reconciliation refuses a live owned process and retains unknown spend; it does
not infer success. Child file/process/container effects retain their existing
reconciliation rules. Transactions, revision comparisons and authenticated
history support audit/recovery. Locks do not coordinate separate stores or
protect against privileged external processes.

## Prepared/manual compatibility

The supervised serial route remains available. `team-start PROJECT` freezes a
prepared workflow without dispatch. `team-request --task TASK_ID --output
REQUEST.json` exports a proposal packet; actual authorized workers return an
AgentStep through `team-submit --task TASK_ID --request-id REQUEST_ID --file
STEP.json`. `team-drive --task TASK_ID --adapter command --argv
'["/absolute/wrapper"]'` or `--adapter codex` performs one bounded local turn.
Native tasks use the file/evaluator route instead of legacy `team-drive`.

After direct child work, `team-collect --task TASK_ID` records verified outputs.
`team-receive --task TASK_ID --handoff-id HANDOFF_ID --role RECIPIENT --decision
accept --note "Actual inspection details"` records actual recipient inspection.
All commands use the same private state. Manual batches remain serial with
per-child budgets and require a reviewed new batch after rejection. See
[native evaluator operations](native-engine.md) for request/sign/import and
resume/verification. Continuous `team-run` owns automatic accounting/repair.
