# 开发 Workflow 审核：一个新需求从进入到完成

场景：你有一个新的产品需求，比如"给订单系统加退款功能"，要求自动完成，并且整个过程看得到、管得住。本文按时间顺序列出每一步由哪个 agent 负责、读什么、产出什么、谁来把关。

## 0. 需求从哪里进来

| 方式 | 命令 / 做法 | 之后会发生什么 |
|---|---|---|
| 一句话需求 | `loop request "加退款功能，支持部分退款" --doc docs/refund.md` | 规划 agent 把需求起草成目标（含验收和评审），排进队列，然后通知你 |
| 在聊天里说 | "用 loop skill，把这个需求建成目标" | 聊天里的 agent 起草，你确认后批准 |
| 已经有路线图 | 写进文档，然后 `loop propose`；或者队列做完后自动提议 | 规划 agent 按文档规划下一批 |

不管从哪里进来，目标都要**你批准后才会开始**。

## 1. 完整流程

| # | 阶段 | 负责的 agent（角色） | 先读什么 | 产出什么 | 把关（控制器检查） |
|---|---|---|---|---|---|
| 1 | 产品简报 intake | **产品经理** product | 你的需求和回答、产品文档、现有功能 | `docs/loop/<目标>/product-brief.md`：问题、用户、旅程、目标、指标、范围和不做的事 | 文档存在且不为空（`loop_stage_done`） |
| 2 | 需求提取 requirements | **需求分析师** analyst | 所有文档，以及其中引用的规格和台账 | 一条条需求（编号、原文出处、验证方式） | 至少一条需求，并且已定稿 |
| 3 | 需求审核 | **产品经理**（独立的只读会话） | 产品简报、需求、原始文档 | 通过，或者退回第 1、2 步 | 审核通过，并且审核的就是当前这一版内容 |
| 4 | 方案设计 solution | **架构师** architect | 需求、代码库、约束 | `solution.md`：多个方案的取舍、选定的架构、接口约定、风险 | 文档已交付 |
| 5 | 测试设计 test_design | **测试设计师** test-designer | 需求、方案、现有测试框架 | `test-plan.md`：每条需求对应的测试用例（层级、步骤、预期结果） | 文档已交付 |
| 6 | 计划与配人 plan | **技术负责人** tech-lead | 需求、方案、测试计划、验收检查 | 任务列表：每个任务标明覆盖哪些需求（covers）、负责角色（role）、**团队配置**（team，例如 2 个后端 + 1 个测试）和检查（checks） | 每条需求都有任务覆盖，每个任务都有检查，团队人数不超过上限 |
| 7 | 资源就绪 resources | **资源规划** resource-planner | 方案、计划、测试计划需要的环境 | `readiness.md`：逐项实测工具、服务、账号、设备是否可用；要花钱或要权限的先请你批准 | 文档已交付 |
| 8 | 计划审核 | **计划审核员**（独立的只读会话） | 第 4–7 步的全部产出、原始文档 | 通过，或者退回方案、测试设计、计划、资源中的任意一步 | 审核通过，并且审核的就是当前这一版内容 |
| 9 | 开发 develop | **按任务的角色**：架构 / 后端 / 前端 / 移动 / 数据 / 测试 / 安全 / 运维；任务有团队配置时，由**调度 agent** 派出多个子 agent | 任务说明、角色说明、交接记录 | 代码和测试 | 每个任务的检查由控制器来跑，必须通过 |
| 10 | 分类测试 test | **控制器**负责执行，失败时由**测试**角色修复 | — | 按 unit → integration → e2e → performance → security → regression → acceptance 的顺序依次运行 | 全部通过 |
| 11 | 代码 / 安全 / 性能评审 | **代码评审员**、**安全专家**、**性能工程师**（性能评审只在有性能要求时出现） | 代码改动、需求、方案 | 通过，或者给出具体到"文件:行号"的问题 | 全部通过，并且评审的就是当前代码 |
| 12 | 最终验收 | **验收负责人** acceptance-lead | 需求 → 任务 → 检查结果的对照表 | 每条需求都有证据，才算通过 | 通过 |
| 13 | 产品验收 | **产品经理** | 产品简报、实际运行出来的产品 | 从用户的角度判断是否符合需求 | 通过 |
| 14 | 人工评审（可选） | **你** | 评审里写好的操作步骤 | 批准，或者说明哪里有问题 | 你批准 |

不通过就退回：
- 审核不通过时，会退回到指定的那一步。退回那一步的 agent 会收到审核意见，修改后再重新审核。
- 测试或评审不通过时，进入修复轮次，修复后重新验证。
- 同一处反复失败超过上限，就会阻塞并通知你来决定。

## 2. 每个角色说明的统一格式

每个角色说明都写清楚四件事：**专注什么 · 先读什么 · 产出什么（用哪个工具提交） · 做到什么程度算完成**。

| 用途 | 角色 |
|---|---|
| 流程中的阶段 | product、analyst、architect、test-designer、tech-lead、resource-planner、plan-reviewer、reviewer、security、performance、acceptance-lead |
| 开发任务 | architect、backend、frontend、mobile、data、tester、security、devops、performance |
| 运维 | sre |
| 排查 | investigator |

- 查看所有角色：`loop roles`。
- 定制某个角色：复制一份到 `.loop/roles/<角色>.md` 再修改；新建一个文件就是新增一个角色。
- 定制某个阶段由谁负责：`.loop/workflows/develop.json`，例如 `{"roles": {"plan": "architect"}}`。
- 为每个角色单独配置模型和推理强度：`agent.roles.<角色> = {adapter, model, effort, skill}`。也可以按阶段配置：`agent.stages.<阶段>`。
- 跳过不需要的阶段：`"pipeline": {"skip": ["intake", "resources", ...]}`。

## 3. 审核结论：已经做到的

- 每一步都有明确的负责角色，以及控制器的把关条件。模型说"做完了"不算数。
- 计划、测试、评审、验收都由**另一个独立的只读会话**来审，可以换另一家的模型。
- 需求能一路追溯到最终验收：需求编号 → 任务的 covers → 检查结果 → 验收对照表。
- 资源和环境问题在开发**之前**就会被发现。这正是 v1 做到一半才发现环境不行的教训。
- 全程都能看到：看板的流水线卡片显示当前在哪一步，每一轮用了什么角色和模型、做了什么，子 agent 的工作也能看到，Telegram 会推送进度。

## 4. 审核结论：还没做到的

1. **任务之间是串行的。** 并行只发生在单个任务内部，靠宿主自带的子 agent 实现。几个互相独立的任务不会同时开工，以后可以用多个 git worktree 来做并行。
2. **子 agent 能不能用指定的模型，取决于宿主工具**（Codex 的 spawn_agent、Claude 的 Task 工具）。Loop 会把每个角色该用的模型写进指令，但没法强制。
3. **在 Telegram 里回复还不能直接回答问题**，目前只能接收通知。
4. **运维 workflow 目前只有一个阶段**：SRE 负责的事件处理。你说之后要升级运维，可以按同样的方式扩展成：监控 → 分诊 → 止血 → 根因 → 修复 → 复盘，每一步配一个角色。
5. **完整流水线只用假 agent 端到端验证过**（68 个测试）。还没有用真实的 Codex 或 Claude 跑完一个完整目标。建议先拿一个小需求试一次，例如 `loop request "…"`。
6. **完整流水线每个目标至少要跑 15 轮左右**，比旧流程更贵。小需求可以用 `skip` 跳过部分阶段。
