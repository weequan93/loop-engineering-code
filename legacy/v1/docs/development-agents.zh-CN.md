# 开发团队的专业 agent

开发场景预设 16 个角色。协调者根据 spec、已回答的问题、现有项目和可用工具
选择实际团队，准备任务、依赖、检查和交接。你提供需求并回答关键问题即可；
日常技术决定由团队结合项目约定处理。

每个角色都有输入、文件范围、交付物、交接对象、完成标准和专业执行流程。
`.loop/agent-protocol.md` 统一规定如何读取需求、处理疑问、提出修改、核对实际
检查结果和报告缺口。这些内容会进入执行器的工作请求、接收交接请求及独立
评审请求。执行器按任务创建请求，并按团队策略管理并行数和累计资源。

## 角色与交付物

| 角色 | 专业工作 | 主要交付物 |
| --- | --- | --- |
| 协调者 `coordinator` | 拆解需求、选人、安排依赖、整合问题和控制返工 | 任务计划、团队决策、需求与证据对应表、交付说明 |
| 需求评审 `requirements_reviewer` | 澄清业务规则、边界、矛盾、兼容要求和验收场景 | 有来源的需求 ID、场景、待确认事项 |
| 产品与交互设计 `designer` | 用户流程、组件状态、响应布局、键盘操作和错误反馈 | 流程与状态说明、设计决定、实现检查结果 |
| 架构 `architect` | 模块边界、数据归属、接口实例、错误语义和技术取舍 | 接口约定、架构决定、实现依赖与偏差 |
| 前端 `frontend` | 组件、页面状态、接口接入、交互与可访问性 | 前端修改、实际检查结果、接口与集成说明 |
| 后端 `backend` | 业务规则、接口、校验、权限、事务和失败处理 | 后端修改、行为检查、兼容与数据说明 |
| 功能测试 `tester` | 正常、错误、边界、集成和回归场景 | 需求与用例对应表、实际日志、可复现缺陷 |
| 安全 `security` | 资产、信任边界、权限隔离、输入输出和敏感数据 | 有依据的风险、修复建议、独立复核结果 |
| 性能测试 `performance` | 提前定义负载和阈值，保留原始测量并分析瓶颈 | 工作负载、环境、指标分布、错误与资源结果 |
| 代码评审 `reviewer` | 独立检查实现、兼容性、失败路径和回归 | 候选版本对应的缺陷与通过／失败／不确定结论 |
| 需求验收 `acceptance` | 独立核对每项需求及功能、质量和人工判定证据 | 逐项验收表、缺口、验收建议 |
| 集成 `integrator` | 共享接口、集成顺序、冲突和组合后的行为 | 整合版本、冲突决定、实际集成检查 |
| 构建交付 `devops` | 构建、打包、CI、运行环境和发布恢复步骤 | 构建日志、产物身份、配置与发布说明 |
| 数据库 `database` | 数据约束、迁移、事务、兼容和恢复 | 数据约定、迁移修改、实际兼容与恢复检查 |
| 文档 `documentation` | 安装、使用、接口示例、排错和移交 | 与实际行为一致的指南、验证过的示例 |
| 可靠性 `reliability` | 健康信号、故障检测、超时、降级和恢复 | 监控配置、运行手册、有范围的恢复结果 |

需求评审、架构、功能测试、协调、独立代码评审和需求验收是必需职责。
其余按项目范围启用。例如页面项目通常启用设计与前端，数据迁移启用数据库，
有性能目标的服务启用性能角色。每个选择都要记录理由和需求或项目依据。

## 兼任与独立检查

小任务可以由预设允许的角色兼任，例如协调者兼任需求评审和功能测试。
当前有效的选择会让兼任者自动收到这些角色的完整流程；各项职责仍要有
自己的结果。具体任务只收到任务角色及兼任者的约定，避免把其他工作的
指令混入该任务。过期或待定的团队选择不会产生有效兼任关系。

安全评审、代码评审和需求验收保留各自的独立上下文或评估器。修复交回实现
负责人，修改后重新获取需要的检查和独立结论。验收会检查整个需求范围，
包括尚未实现的部分；某个任务通过自己的检查，不能代表整个项目验收通过。

结果要说明需求 ID、检查或评估过程、具体候选版本、环境、实际证据及缺口。
缺少必需工具或证据会保持待处理；性能阈值不能在看到结果后调低，测试预期
不能为迁就实现而削弱。必须由人判断的事项仍由实际用户决定。

## 安装和更新

首次使用与已有项目更新按[重新设置指南](reinitialize.zh-CN.md)操作。
普通 `init` 保留已有自定义文件；要安装当前完整角色包，可先停止旧团队，
再使用指南中的 `reinit`。该命令归档旧配置并保留项目代码与历史。

新开发场景的上下文上限默认为 `120000` 字节，便于容纳完整角色职责及证据。
普通初始化保留已有 `.loop/project.json` 的上限；需要调整时在团队启动前
明确编辑。超过上限会拒绝请求，必需职责和指令不会为了适配而被悄悄丢弃。
调用次数、时间和金额限制继续由团队策略及实际 provider 能力决定。

## 当前验证范围

离线验证覆盖完整角色上下文、兼任职责、交接接收者、独立评估请求、冻结输入
和实际本地检查。模型输出和专业判断使用可控测试数据，实际模型的专业质量
需要另行验收。配置角色后，根据项目需要提前设置[执行工具](execution-tools.zh-CN.md)，
即可使用依赖准备、浏览器断言/截图和有界 HTTP 工作负载。缺少真实环境或
匹配执行器的必需检查保持待处理；发布和其他压力/扫描工具仍单独接入。当前 Desktop 桥接仍需实际客户端
兼容验证；参考[团队执行](team-execution.md)和[Desktop 接入](desktop-mcp.md)。
