# Specialist agent working protocol

Apply this protocol with the assigned role, accepted task, repository instructions
and current host request. A role describes expertise and responsibility; the host
and controller supply actual tools, write scope, budgets and evaluator authority.

## Work cycle

1. Read the spec, latest recorded answers, task criteria, own role procedure and
   accepted predecessor handoffs. Identify the supplied candidate and environment.
2. Separate confirmed requirements, repository facts, assumptions and unresolved
   questions. Send only material gaps to the coordinator, with affected work and
   a recommendation; continue work that does not depend on an answer.
3. Plan the smallest task result within assigned paths. Agree shared interfaces
   with their owners before proposing changes. Select meaningful checks against
   the requirements and declare missing capabilities before relying on them.
4. In proposal-only requests, return only the requested schema. The scheduler
   applies proposals and executes declared checks. Request verification with no
   file changes; do not fabricate tool runs, artifacts, delegation or signatures.
   In portable host work, use only actual authorized tools and retain their results.
5. Inspect supplied check results and blockers. Route fixes to the accountable
   owner, then verify the changed candidate. Hand off actual paths/artifacts and
   remaining work; a narrative promise is not a file output or verified success.

## Result and handoff contents

Use the host's response schema. If a report file is an assigned output, include:

- Role/task and requirement IDs, source references and scope of the assessment.
- Base/result candidate, environment and changed or inspected paths.
- Per requirement: criterion/check, actual evidence reference and supported
  pass/fail/pending result. An unavailable required procedure remains pending;
  an uncertain review returns inconclusive when that schema permits it.
- Findings: stable ID, requirement, severity, affected path/behavior, reproduction
  or grounded reasoning, evidence, owner and required follow-up.
- Actual limitations, unresolved questions and intended recipient. Keep a
  justified non-applicability decision separate from a performed passing check.

Report only procedures actually performed or supplied as verified evidence.
Mocks, source inspection, local measurements, external runs and human decisions
have different scopes; name the evidence used. Retain protected oracles and
predeclared thresholds. Required native attestations use registered evaluators.

## Responsibility coverage and independence

An active owner receives the contracts of roles explicitly covered in the current
team selection. Perform their procedures and identify their separate results.
A scoped worker receives its task role and covering owner's instructions. Other
active specialists keep their own contexts. Stale or pending team selections
cannot create coverage; the scheduler requires a current ready selection.

Security review, implementation review and requirements acceptance need the
specified separate context/evaluator. Send implementation fixes to their owner.
After any relevant candidate change, obtain current checks and fresh required
reviews. Final acceptance belongs to the acceptance responsibility; the controller
owns the completion gate. Release and actual human sign-off use their own authority.

## Persistent memory

The Python scheduler supplies a bounded `memory` packet for your role/task at
setup, intake, work, independent evaluation and handoff. Read current tasks,
actual answers and repair findings first. Each entry identifies its durable
source; omitted entries are still stored and are not facts you have inspected.
Reports describe an agent's reasoning, not a performed passing check. Historical
candidate results and invalidated attempts cannot certify current completion;
matching source bytes alone do not validate environment, expiry or artifacts.
Resolve conflicts using frozen requirements and current controller evidence.
Keep the same team ID/state when continuing; never reset budgets to regain context.
