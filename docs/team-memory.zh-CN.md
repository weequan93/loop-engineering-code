# 团队记忆与上下文

`loop.py` 每次调用角色时，从私有状态中的签名检查点和项目中已绑定的需求文件生成记忆包。记忆不是聊天窗口历史，也不需要额外的模型总结调用。

记忆分为需求与真实回答、任务进度、返工原因、检查与交接索引、角色报告和已失效的历史尝试。每条记录保留来源。协调者查看整个批次；专业角色查看自己的任务、依赖和相关交接。独立评审的记忆包排除实现者的未经验证的总结与收件意见。

任务、需求和仓库规则仍是必需上下文。记忆按优先级在 UTF-8 字节预算中选择，超出的条目留在持久状态中，并报告省略数量。缩小上下文不能删除必需规则或把没有看到的资料当成已读。

默认记忆预算按 profile 的上下文上限分配，并限制在 2–32 KiB。查看时的 `--max-bytes` 只控制导出大小；模型请求仍受 profile 的整体上限约束。这个筛选用于控制相关性和篇幅，角色能读取哪些项目文件仍由已有任务与运行环境规则控制。

检查索引包含候选版本、环境和证据引用。候选版本不同的结果标为历史；返工前的尝试始终标为已失效，即使文件内容后来恢复一致。记忆不能替代控制器重新验证、独立评审或真实用户回答，也不能授予工具权限。

暂停、重启或更换宿主后，继续同一个 `team_id`，会重新读取同一份持久记录和累计预算。不同项目或新批次不自动导入旧 agent 结论。跨批次长期需求应保留在 spec、真实问答和项目文档中；旧批次的私有日志仍保留。`team-memory` 要求该批次的冻结输入仍然匹配；输入已经变更时拒绝把新需求混入旧记忆。

本次实现和验证只使用离线 fixture、真实本地检查和持久状态，不调用真实模型。离线测试证明记录传递与失效规则，不证明模型会正确理解所有记忆。

## 查看与继续

从框架目录执行，替换实际的 `TEAM_ID` 和私有状态路径：

```bash
.venv/bin/python scripts/loop.py team-memory TEAM_ID \
  --state-dir /absolute/private-state
.venv/bin/python scripts/loop.py team-memory TEAM_ID \
  --state-dir /absolute/private-state --role backend --task TASK_ID \
  --max-bytes 65536
```

查看不调用模型，也不增加预算或创建子任务。输出包括来源引用、当前候选版本、`coverage.omitted` 和失效标签。`agent_report` / `stage_report` 是 agent 报告；`check_index` / `handoff_index` 只是持久证据索引；`invalidated` 是返工前已撤销的尝试；`historical_candidate` 是其他版本的结果。`candidate_match` 只表示文件版本一致，不保证环境、证据有效期或外部状态仍然有效。

控制器在安装 spec/任务文件时同时提交阶段报告。安装途中崩溃的报告不会提前进入角色记忆；恢复后只提交一次。每次提案、真实检查、返工和收件确认沿用现有签名日志。报告或问答过大时，整条省略，完整原文仍保留；检查点中的过长状态说明使用有标记的预览。

需求和规划请求在派发前冻结记忆包。模型已返回、结果尚未处理时中断，恢复使用已收到的响应；内部日志版本或用量记录增加不会导致重复推理。明确失败或已协调解决的失败调用则生成包含失败原因的新上下文，重试仍计入原批次预算。

继续执行时使用原来的私有状态和批次：

```bash
.venv/bin/python scripts/loop.py team-run --team-id TEAM_ID \
  --state-dir /absolute/private-state --adapter codex
```

这是显式模型调用。等待真实输入、未解决操作或冻结文件变化时，先处理对应原因；记忆机制不解除这些限制。已有项目无需重新初始化，框架会为已有记录生成记忆；旧批次中从未记录的规划总结不会补造。
