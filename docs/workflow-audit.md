# 开发 Workflow 审核：一个新需求从进入到完成

场景：你有一个新的产品需求，比如"给订单系统加退款功能"，要求自动完成，并且整个过程看得到、管得住。本文按时间顺序列出每一步由哪个 agent 负责、读什么、产出什么、谁来把关。

## 0. 需求从哪里进来

| 方式 | 命令 / 做法 | 之后会发生什么 |
|---|---|---|
| 一句话需求 | `loop request "加退款功能，支持部分退款" --doc docs/refund.md` | 规划 agent 把需求起草成目标（含验收和评审），排进队列，然后通知你 |
| 在聊天里说 | "用 loop skill，把这个需求建成目标" | 聊天里的 agent 起草，你确认后批准 |
| 已经有路线图 | 写进文档，然后 `loop propose`；或者队列做完后自动提议 | 规划 agent 按文档规划下一批 |

不管从哪里进来，目标都要**你批准后才会开始**。

## 1. 完整流程

| # | 阶段 | 负责的 agent（角色） | 先读什么 | 产出什么 | 把关（控制器检查） |
|---|---|---|---|---|---|
| 1 | 简报 brief | **需求分析师** analyst | 你的需求和回答、产品文档 | `docs/loop/<目标>/brief.md`：问题、用户、旅程、成功标准、范围和明确的不做清单；加上**本目标**的需求（编号、出处、验证方式，建议不超过约 20 条） | 文档已交付，需求已定稿 |
| 2 | 设计与计划 design | **技术负责人** tech-lead | 简报、需求、代码库、约束、验收检查 | `design.md`：方案与取舍、对不确定需求先做的可行性验证、资源核实；任务列表（covers、role、team、checks，建议不超过约 20 个）。**任务的检查就是测试设计** | 文档已交付；每条需求都有任务覆盖，每个任务都有检查 |
| 3 | 设计评审 design_review | **设计评审员**（独立只读会话） | 原始文档、简报、需求、设计和计划 | 通过；或者只为“会让目标错误或做不成”的问题不通过，退回 brief 或 design | 最多 2 轮，之后由你决定 |
| 4 | 开发 develop | **按任务的角色**；任务有团队配置时由调度 agent 派出子 agent | 任务说明、角色说明、交接记录 | 代码和测试 | 每个任务的检查由控制器来跑，必须通过 |
| 5 | 分类测试 test | **控制器**负责执行，失败时由测试角色修复 | — | 按 unit → integration → e2e → performance → security → regression → acceptance 依次运行 | 全部通过 |
| 6 | 综合评审 final-review | **最终评审员** acceptance-lead（一个只读回合，可以用子 agent 并行看各个角度） | 需求 → 任务 → 检查结果的对照、代码改动、简报 | 从这些角度给出一个结论：需求核对、代码、安全、性能（有性能要求时）、功能（按用户旅程），以及目标自己定义的评审 | 通过；最多 2 轮，之后由你决定 |
| 7 | 人工评审（可选） | **你** | 评审里写好的操作步骤 | 批准，或者说明哪里有问题 | 你批准 |

不通过就退回：
- 设计评审不通过时，退回 brief 或 design，修改后再评审；**连续 2 轮不通过就交给你决定**：`loop review <id> pass` 接受，或者修改后 `loop unblock` 再来一轮。综合评审同理。
- 设计评审通过以后，开发中修改任务不会再触发评审；只有出现没有任务覆盖的需求，才回到设计阶段补上。
- 测试不通过时进入修复轮次，修复后重新验证。
- 失败的评审和重复提交不算“有进展”，所以原地打转会被及时发现。

## 2. 每个角色说明的统一格式

每个角色说明都写清楚四件事：**专注什么 · 先读什么 · 产出什么（用哪个工具提交） · 做到什么程度算完成**。

| 用途 | 角色 |
|---|---|
| 流程中的阶段 | analyst（简报）、tech-lead（设计与计划）、plan-reviewer（设计评审）、acceptance-lead（综合评审） |
| 开发任务 | architect、backend、frontend、mobile、data、tester、security、devops、performance |
| 运维 | sre |
| 排查 | investigator |

- 查看所有角色：`loop roles`。
- 定制某个角色：复制一份到 `.loop/roles/<角色>.md` 再修改；新建一个文件就是新增一个角色。
- 定制某个阶段由谁负责：`.loop/workflows/develop.json`，例如 `{"roles": {"design": "architect"}}`。
- 为每个角色单独配置模型和推理强度：`agent.roles.<角色> = {adapter, model, effort, skill}`。也可以按阶段配置：`agent.stages.<阶段>`。
- 跳过评审：`"pipeline": {"skip": ["design_review", "final-review"]}`。

## 3. 审核结论：已经做到的

- 每一步都有明确的负责角色，以及控制器的把关条件。模型说"做完了"不算数。
- 设计和最终结果各由**一个独立的只读会话**审一次，可以换另一家的模型。
- 需求能一路追溯到最终验收：需求编号 → 任务的 covers → 检查结果 → 验收对照表。
- 资源、环境和可行性问题在开发**之前**的设计阶段就要验证。这正是做到一半才发现做不到的教训。
- 全程都能看到：看板的流水线卡片显示当前在哪一步，每一轮用了什么角色和模型、做了什么，子 agent 的工作也能看到，Telegram 会推送进度。

## 4. 审核结论：还没做到的

1. **任务之间是串行的。** 并行只发生在单个任务内部，靠宿主自带的子 agent 实现。几个互相独立的任务不会同时开工，以后可以用多个 git worktree 来做并行。
2. **子 agent 能不能用指定的模型，取决于宿主工具**（Codex 的 spawn_agent、Claude 的 Task 工具）。Loop 会把每个角色该用的模型写进指令，但没法强制。
3. **在 Telegram 里回复还不能直接回答问题**，目前只能接收通知。
4. **运维 workflow 目前只有一个阶段**：SRE 负责的事件处理。你说之后要升级运维，可以按同样的方式扩展成：监控 → 分诊 → 止血 → 根因 → 修复 → 复盘，每一步配一个角色。
5. **完整流水线只用假 agent 端到端验证过**（68 个测试）。还没有用真实的 Codex 或 Claude 跑完一个完整目标。建议先拿一个小需求试一次，例如 `loop request "…"`。
6. **完整流水线每个目标至少要跑约 5 轮**（简报、设计、设计评审、开发、综合评审），再加上任务本身的回合。小需求可以用 `skip` 跳过评审。
