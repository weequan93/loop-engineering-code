# 在 Codex / Claude 的对话中使用 Loop

最新[协调与恢复机制](native-autonomy.md)支持独立任务同时在各自副本开发、串行整合验证，按声明依赖保留未受影响的实测观察，并在计划阶段检查实际评审时限与返工预留。进度页区分宿主活动报告、实际经过时间和控制器记录时间。连接时使用 `loop_handshake` 核对框架与技能版本；旧批次和已有回答不会自动迁移。

这个入口让当前 App / CLI 的主 agent 负责需求对话和专业分工。Loop 提供项目工具，保存状态、应用受约束的修改、执行检查和验证交接。用户在同一个聊天里提供需求、回答问题、查看进度；日常操作由主 agent 完成。

`native-host` 与原来的 `team-run` 是两种执行入口。前者使用已经打开的宿主对话，日常协调不调用模型，也不需要另开一个终端调度器。明确登记独立评审执行器后，`loop_evaluation_run` 可以运行有界的新评审上下文；详见[独立评审接入](native-review.zh-CN.md)。后者继续提供独立的自动调度、累计预算和隔离并行工作区。已有团队的记录和预算不能静默转换。

## 一次性接入

在 Loop 仓库的已配置环境中执行：

```bash
.venv/bin/python scripts/loop.py host-install /absolute/path/to/your-project \
  --state-dir /absolute/private-state --host codex
```

安装器只合并当前项目的 `.codex/config.toml` 并加入
`.agents/skills/loop-engineering/`。它保留其他配置，遇到不同的同名服务器或
已修改技能会拒绝覆盖。相同配置可以重复安装。它不会初始化开发任务、修改
spec、取消旧团队、登录账号、调用模型或修改全局设置。
安装器可以升级字节完全匹配的旧版官方技能；用户编辑过的版本仍会被保留。

用 Codex App 或 Codex CLI 打开并信任这个项目，重新连接项目 MCP 工具。
在聊天中输入：

> 使用 $loop-engineering。从项目 docs 收集需求，组织开发团队，并在这个聊天里展示进度。需要我决定的事情直接问我。

CLI 可以使用同一项目技能。实际客户端需支持项目配置和本地 stdio MCP；
安装成功表示配置文件已准备好，不能证明 App 已加载服务器或模型团队已运行。
未看到 `loop_begin` / `loop_progress` 等工具时，先检查宿主的 MCP 连接状态。
移动 Loop 仓库或删除其 Python 环境后，需要更新服务器的绝对路径。

## 在 Codex App 中具体怎么操作

以已安装接入文件的 macare 为例：

1. 在 App 的项目列表里打开 macare；尚未添加时，添加本地项目并选择
   `/Users/super/Documents/ai/macare`。该目录应是项目的主目录，新的聊天才能
   自动发现这里的技能和配置。
2. 在 macare 下新建一个 Codex 聊天，选择本机的 **Local / 本地** 环境。
   这个安装绑定上述目录；另一个工作区需要为它自己的目录重新安装接入文件。
3. 在新聊天中发送下面这段话。主 agent 应先读取保存的状态、提供进度入口，
   再核对资料和需求。当前聊天属于 Loop 框架仓库时，先转到 macare 的聊天使用。

> 使用 $loop-engineering。先检查现有团队并保留历史记录，切换到对话模式。
> 从 docs 收集和核对需求，沿用现有里程碑和停止条件，列出需要我确认的问题。
> 确认范围后组织开发团队。请打开进度页，并在聊天里报告阶段进度。

4. 直接在聊天里回答需求问题；已有 spec 会被核对，不要求从空白重新写一份。
   最后一个必须回答的问题确认后，主 agent 应自动继续汇总规划、提交正式任务，
   再派发开发工作。中途问进度时，它应先回答再继续原来的工作。
   未满足的需求、能力或评估器会显示为具体阻塞。
5. 点击 agent 给出的进度链接，或说“打开进度页”。页面显示当前阶段、任务、
   检查、待回答问题和阻塞；也可以直接问“谁在做什么，下一步是什么”。
6. 要暂停就说“暂停当前团队”；回来后在同一聊天说“继续原来的团队，先报告
   保存的进度”。如果换了聊天，明确要求读取原团队记录后继续，保留已有历史。

技能或工具没有出现时，先重新打开项目并新建聊天；仍未加载时重启 Codex。
在设置的 MCP 服务器列表中检查 `loop-native`，也可以在聊天输入 `/mcp`
查看连接。技能已加载但工具未连接时，可以直接让主 agent 检查连接并报告原因，
此时不能声称团队已经开始执行。

如果更喜欢 Codex CLI，只需在目标项目中启动一次交互会话：

```bash
codex --cd /Users/super/Documents/ai/macare
```

然后发送同一段启动话语，后续通过对话回答问题、查看进度、暂停和继续。
工具不会在主 agent 的回合结束后自行运行模型；退出宿主并关闭 MCP 连接后，
页面只保留最后快照。重新连接后，由主 agent 根据保存的记录继续。

Claude Code 的接入方式：

```bash
.venv/bin/python scripts/loop.py host-install /absolute/path/to/your-project \
  --state-dir /absolute/private-state --host claude-code
```

它加入 `.claude/skills/loop-engineering/SKILL.md` 并合并 `.mcp.json`。
重新连接 MCP、按客户端要求启用项目服务器，然后使用 `/loop-engineering`。

Claude Desktop 的本地服务器需要在客户端注册：

```bash
.venv/bin/python scripts/loop.py host-install /absolute/path/to/your-project \
  --state-dir /absolute/private-state --host claude-desktop
```

这个命令导出 `.loop/claude-desktop-native-mcp.json` 和
`.loop/native-host-instructions.md`，不修改 Desktop 的全局设置。
把 `loop-native` 条目合并到客户端的本地 MCP 配置，重新连接，并将说明作为
该项目的对话指令。它与旧的 [Desktop 请求队列](desktop-mcp.md) 不同；
旧入口仍需终端调度器，新入口由当前对话调用工具。

只想预览配置而不写入宿主文件时，用 `host-config` 替代 `host-install`。
三个入口都固定绑定一个项目和一个项目外的私有状态目录。

## 日常使用

可以直接说：

- “从 docs 帮我整理 spec，有疑问再问我。”
- “按已经确认的范围继续开发，每个阶段告诉我进度。”
- “现在谁在处理什么？还有哪些检查没通过？”
- “暂停；稍后接着原来的团队继续。”

主 agent 先读取实际进度，再连接同一个 native 团队。空 spec 进入 SPEC；
已准备 spec 进入 INTAKE；已准备任务合同进入 EXECUTION。
需求阶段读取实际资料、保存草案和问题；回答后刷新上下文。协调阶段根据 spec
选取现有十六个专业角色，准备任务、依赖、输出和检查。应用修改、检查和交接
由 Loop 工具处理，保留原项目的里程碑停止条件。

## 连续推进与停下来的原因

主 agent 用 `loop_next` 获取当前实际下一步：SPEC 提供需求请求，INTAKE 提供
规划请求，任务计划通过后提供已满足依赖的工作者请求，之后继续实测检查、
指定角色交接和最终验收。`loop_plan_submit` 接收原生 JSON 对象，仍使用已有的
冻结请求、任务合同、范围和评估器校验，不省略独立评审或人工验收。

开发任务优先使用 `loop_workbench_prepare`。它准备绑定当前任务请求的独立
工作副本，并返回副本路径和上下文文件。专业 agent 可以用宿主的文件工具在
这个副本中正常写代码，返回简短的文件和结果说明；不必把整个实现塞进一份
代码 JSON。主 agent 通过 `loop_workbench_submit` 收集稳定修改，Loop 再校验
原范围、候选和版本化文件操作，并运行原来的检查。共享项目只有这次受控集成
才会变化，角色聊天和副本里的试运行都不代替验收证据。

`loop_workbench_status` 展示副本中实际修改的文件和等待期限。期限沿用
`team-policy.json` 的 `timeout_seconds`，通常为 180 秒；刷新页面和重复请求都
不会重置它。超时后下一步明确要求停止空等：主 agent 中断自己拥有的慢工作者，
检查已经写下的草稿，再自行接手或有界重新分配。同一子运行的迭代和已记录的
控制器执行时间累计保留；宿主模型在控制器操作之外的等待时间、token 和费用
不在控制器账本内。这是需要宿主执行的等待期限，不是后台强制中断。重新分配
后旧副本仍保存，但旧请求不能混入新候选；有用文件需要
经过核对再带入新副本。Loop 本身不能中断或唤醒宿主模型。

这个副本共享宿主的系统权限，提供文件分离，不是受保护运行时。可移植的
`loop_task_request` / `loop_task_submit` 提案接口仍可用于小修改和纯文本宿主。
用户暂停、缺失评估器和控制器上限仍然优先，不能为赶进度绕过。

## 主线程如何协调专业 agent

正式父任务仍按依赖和原控制器门禁执行；一个已派发的开发任务可以在协调工作
副本内拆成多个专业子任务。主线程先明确依赖、公共接口和文件归属，再把独立
工作交给适用的专业 agent。子任务不增加正式验收范围，也不改变父任务的冻结
合同、权威检查和预算。十六个角色是选择库，按实际工作启用。

四个工具把这次分工和实际交接写入记录：

| 工具 | 主线程的操作 |
| --- | --- |
| `loop_worker_assign` | 登记专业角色、具体目标、输入、互不重叠的写入文件名单、依赖、交付和期限，先获得 `PREPARED` 记录及子工作副本，再通过宿主启动实际 worker。 |
| `loop_worker_update` | 将分配记录绑定宿主返回的实际 agent ID，更新实际状态与具体 `detail`，说明已做工作、文件、结果或阻塞；不能将准备完成写成 agent 已经运行。 |
| `loop_worker_collect` | 在工作者停止写入后，检查稳定子稿并串行合入协调副本；成功收集后标为 `COLLECTED`，随后依赖它的子任务才可派发。 |
| `loop_dispatch_board` | 查看登记的实际身份、专业角色、目标、实际修改文件、槽位和期限，选择当前可派发工作，并找出应接手的慢工作者。 |

`max_parallel` 使用当前团队的冻结配置；主线程还要遵守宿主实际可用槽位。
准备分配不启动模型，模型由主线程使用宿主工具实际启动、停止和等待。按准备
结果再派发，任务完成或出现阻塞后及时收集、补位，不等待整批 agent 全部返回。
并行工作者必须各用自己的副本，写入文件名单不能重叠，也不能超出原合同。
已声明的依赖子任务须先 `COLLECTED`。必需子任务未收齐时，工具拒绝最终
`loop_workbench_submit`；收齐后仍由原父任务检查和正式交接决定是否通过。

例如，主线程先让架构专家完成公共接口并收集到协调副本。之后可将服务实现
交给后端专家、界面实现交给前端专家，两者在不同文件的副本中工作。测试专家
可以只读分析接口、准备检查建议；咨询也占运行槽位。如果配置只允许两个
并行工作者，测试咨询就安排在接口阶段或一个实现工作者结束后。主线程保留
整合职责，逐份收集，再运行原检查；无须为了这个例子增大并行配置。

独立安全、评审和验收角色可以提供只读咨询，帮助提前发现问题；咨询结果不
代替已注册评估器的签名评审。专业子任务的文件、检查建议和宿主声明也不等于
原父任务通过。候选变化后，更新有关上下文并重跑受影响的检查和正式评审。
达到工作者期限时，主线程检查草稿、停止自己拥有的慢工作者，再接手或有界
重新分配。刷新派发板不续期，MCP 无法自行中断模型；副本仍共享系统权限，
原生模型等待、token 和费用仍在控制器账本之外。
该入口限制已登记的并行槽位、单个工作者期限及 128 条分工记录；自动执行入口的
全团队派发、返工和模型等待总量并未在原生宿主中实施。准备副本后、登记之前
中断可能留下未登记临时草稿，不会因此启动模型或修改正式项目。

每个结果都有 `next_action`。`continue_work=true` 表示当前仍有可执行的工作；
主 agent 应继续调用工具，不能只回复“正在准备任务契约”然后结束回合。
剩余问题、暂停/取消、资料冲突、缺少评估器、实际工具失败、控制器限制和已完成
的里程碑会给出停止原因。多个问题的回答依次写入；只有最后一个必须回答的问题
完成后才离开等待状态，已给出的答案不需要重新询问。

规划时启动原生子 agent 会产生宿主内部活动，但不会自动生成 Loop 任务。
主 agent 先用 `loop_planning_activity` 记录实际分工和实际返回的规划结果，再汇总
为完整任务计划。通过计划校验后，正式任务才进入任务列表并可被派发。
规划活动只是宿主汇报，不能作为开发已完成或独立验收通过的证据。

这条连续流程依赖宿主正在运行主 agent。MCP 返回状态、上下文和受约束的工具，
无法在宿主已经结束回合或关闭之后自行调用模型或重新启动主 agent。
离线串联验证覆盖控制器转移和真实本地检查；真实模型是否遵守持续执行规则
仍需要在具体宿主中观察，不能由技能说明或工具存在直接证明。

专业分工可以使用宿主真正提供的 sub-agent。没有该功能的客户端只能依次覆盖
角色，不能把角色文档称为已经运行的多个 agent。协调分析和任务内专业副本
可以在实际槽位及依赖允许时并行；新计划启用 `native_parallel` 并声明独立文件归属后，
正式任务也能同时在各自副本开发。子稿收集、修改整合与正式检查仍串行处理。
它不会创建另一个用户聊天来模拟工作者。

## 能看到的进度

`loop_progress` 返回当前阶段、角色任务、已完成/总任务数、实测检查、待回答问题、
交接、阻塞原因、实际下一步和最近控制器记录，并生成 `dashboard_url` 指向的本地进度页。
需求与规划区显示已回答/剩余问题，以及主 agent 登记的实际规划分工和结果。
正式计划未提交时显示“计划待提交”，不再用空的 `0/0` 暗示没有发生任何工作。
未登记的宿主活动仍不会被自动读取；不同请求或候选的活动会标为历史规划。
专业派发板显示主线程登记的实际 worker 身份和分工，以及副本里已写下的文件、
槽位占用和期限。`PREPARED` 表示准备了分配，绑定真实 agent 后才能报告运行；
`COLLECTED` 表示子稿已合入协调副本，仍不计为正式父任务或验收完成。
主 agent 应在关键阶段和持续工作期间至少每分钟更新聊天进度。
宿主有浏览器面板时可以直接打开页面，也可以点击链接查看；终端使用文字进度。
查看器只监听 `127.0.0.1`，采用随机链接，只提供该连接登记的进度 HTML，没有
控制、密钥或任意文件接口。无法启动本地查看器时，使用 `dashboard_path` 的 HTML 快照。

页面每三秒刷新，MCP 连接期间由服务更新实际控制器状态。连接关闭后保留最后
快照，不能将它称为实时进度。正式任务数仍然是控制器记录的真实数量，不估计百分比或 ETA。
检查记录绑定各自候选版本；最终候选只有在 COMPLETE 且
`final_candidate_current=true` 时才可声明这一批合同完成。

进度页展示的是 Loop 实际记录的阶段和任务，不能读取宿主内部的每一个思考步骤、
原生 agent UI 或账户用量。这一版没有声称为 Codex / Claude 增加新的原生任务面板。

## 证据、预算和恢复边界

原生主 agent 和 sub-agent 的模型调用不在自动调度器账本里，token / 费用未知。
配置了团队硬 token / 费用上限时，这个入口拒绝开始；需要保留有计量能力的
provider 入口，或显式评审预算策略。任务自身要求的能力和检查也不会被删除。
等待用户或原生模型时没有 `team-run` 的三分钟模型子进程超时；实际检查仍有
自己的时间与能力约束。

原生 agent 的评审文字和交接回执属于宿主声明。这个通用 MCP 接口无法证明
哪个 sub-agent 写了回复，不能签发独立评审的通过证据。要求独立评审、人工确认、
浏览器操作或负载实测的任务，必须使用对应的已注册评估器和真实结果。
`loop_evaluation_run` 可运行已注册执行器；
`loop_evaluation_request` / `loop_evaluation_import` 可请求并导入合法签名结果。
缺失执行器时显示阻塞，不将普通聊天回复转换成验收通过。

中断后继续原来的 native team。工具从持久记录重建
[角色记忆](team-memory.zh-CN.md)，恢复已记录的阶段写入；资料或控制文件被用户
修改时拒绝静默覆盖。暂停需要实际继续指令，取消是终态。已有 `team-run`
团队会阻止 native 接管，主 agent 先显示其状态；只有用户授权停止或切换模式后
才能取消它并开始新团队。未结算调用、进程或文件操作需先在原入口处理。

## 工具与验证范围

`scripts/native_mcp.py` 提供二十五个受项目范围约束的 stdio MCP 工具：开始/进度、
角色上下文、阶段请求/提交、真实回答、任务请求/提交/收集、交接、生命周期、
记忆、连续下一步、对象式计划提交、规划活动、工作副本准备/查看/提交、
专业工作者分配/更新/收集、派发板和三种评估器操作。
不提供通用 shell、任意路径读取、模型 sampling 或密钥导出。
MCP 传输复用已验证的 2025 协议族，新客户端可以协商兼容版本。

离线验证采用确定性 spec/plan/AgentStep、实际本地检查、签名评估器 fixture、
stdio 子进程和故障恢复，不调用真实模型。完整离线检查与实现清单通过后，仍需
另行验证具体客户端的技能/MCP 加载、原生 agent 分工和真实项目使用体验。
离线通过不会自动开始该验证，也不证明语义需求、部署隔离或真实模型效果。

### 评审返工与逐项验证

新批次可在计划中声明有界 `native_rework`，并为评审任务指定 `repair_task`。
`loop_next` 会在符合条件的失败评审后提供 `loop_rework`，保留原子任务、累计用量、
旧证据和交接记录，重开修复责任任务及受影响后续任务。不会自动修改旧批次的冻结配置。

对浏览器、桌面或模拟器实测，可声明 `extensions.verification_scenarios`，通过
`loop_verification_begin`、`loop_verification_update`、`loop_verification_progress`
保存每项实际观察及附件。中断或结果未知的动作必须先核对，不能因为重连就再次执行。
这些宿主记录用于进度与恢复，不能代替独立评估或原合同检查。
详见 [恢复协议与示例](native-rework-verification.md)。
